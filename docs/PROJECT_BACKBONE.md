## 2. 总体架构

- 发行形态是一个客户端 mod ID、一个客户端入口、一个 JAR；各功能作为源码级内部模块维护，不做嵌套 JAR 外壳。
- 总控使用原生 Minecraft `Screen`，不引入 WebView、Cloth Config 或 YACL；Mod Menu 只能作为可选总入口，且其可用性不得依赖 Xaero 是否存在。
- 内部模块之间通过清晰的 provider/bridge 边界连接；外置模块存在且桥接兼容时，外置模块优先。
- 外置模块接管后，内置对应模块必须零初始化：不构造控制器、不注册事件、不启动线程、不读写对应配置。
- 所有复杂工具都必须保留父 Screen；关闭、Esc 和返回应恢复同一父 Screen。父上下文失效时安全返回游戏并给出一次提示。

## 3. 总控与 UI 固化要求

- 左侧固定导航顺序：总览、奥术 HUD、卷轴计算、饰品配装、发酵与厨具、SIMMC 网页地图、预留板块、工具组按键；诊断与日志固定在底部。
- 总览必须说明鼠标入口、快捷键、外置模块接管和当前运行状态。
- 总控和子页面使用中文；长警告、状态和按钮文字必须在不同 GUI 缩放与分辨率下可读、不截断、不重叠。
- 工具组按键进入专属设置页，不跳转 Minecraft 原生控制页；专属页只管理六个组合子键，显示当前键、修改、恢复和冲突提示。
- `\\` 前缀、主键盘 `0` 和内部 Simes 的 `O` 保留为 Minecraft 原生 `KeyBinding`；外置 Simes 存在时不注册内部 `O`。
- 鼠标点击是与快捷键并行的完整入口。快捷键不得拦截按钮点击、滚轮、拖动物品、容器交互、地图操作或原生 Screen 返回。
- 容器名称、聊天和 HUD 信息不能互相遮挡；发酵/厨具以 Simes 原生世界投影为运行时主显示，总控页面只显示状态摘要，不保留重复的右上角全局提示。

## 4. 快捷键与输入边界

默认组合键如下：

| 组合键 | 功能 |
| --- | --- |
| `\` + `1` | 奥术 HUD |
| `\` + `2` | 卷轴计算 |
| `\` + `3` | 饰品配装 |
| `\` + `4` | 发酵与厨具 |
| `\` + `5` | SIMMC 网页地图 |
| `\` + `` ` `` | 诊断与日志 |
| 主键盘 `0` | 饰品工具直达 |

- 按住前缀键后在 750 ms 窗口内按次键；单独松开前缀键打开工具组总览页，工具组按键页只能从总控导航进入。
- 默认键暂不使用 F1-F12、Insert/导航区、SysRq、小键盘和方向键；玩家重绑定时可以选择这些区域。
- 文本框、聊天、命令、书、告示牌和其它编辑界面聚焦时，组合键完全旁路，不吞字符。
- 超时、Esc、未知次键、失焦、切屏和全部鼠标事件都应清除前缀状态并放行原生行为。
- 冲突提示只说明工具组内部冲突；重绑定不能破坏鼠标入口。

## 5. 内置模块与外置桥接

### 5.1 奥术 HUD

- 使用已获得许可的 Simes 功能范围，实现奥术冷却、吟唱/持续状态、公共冷却和法杖魔力 HUD。
- Simes 源码中的 `ArcaneCooldownHud`、`ArcaneStatusHud`、`ManaHud` 和位置配置是行为基线；Tool Set 的生命周期、外置优先和配置隔离规则优先于直接复制 Simes 的入口代码。
- Action Bar、BossBar 和法杖使用的经验包是状态来源；法杖魔力包仅在目标服、内置模块启用、主手持法杖且 Mana HUD 开启时与原版经验分离。
- 设置必须保留奥术冷却、吟唱与持续状态、法杖魔力三个开关及 Simes HUD/原版 Action Bar 模式；统一布局页同时编辑冷却、状态、公共冷却和 Mana 四个 HUD。
- 仅在规范化地址为 `play.simmc.cn` 时激活；离服、切服或客户端停止时清空状态。
- 检测到外置 Simes 时，内置 HUD 不初始化，由外置版接管。

### 5.2 发酵与厨具

- 发酵提示和厨具提示是两个独立开关，默认开启。
- 正确触发流程是开启开关、连接 `play.simmc.cn`、准星指向十格内目标，
  发酵桶再用主手烹饪钟交互以取得服务器校准消息；信息卡是目标上方的
  世界投影，不是固定右上角提示。没有按该流程取得日志/截图时，报告保持
  “未复现/待验证”。
- 仅在 `play.simmc.cn` 激活；准星指向 10 格内目标方块时，在目标上方显示带食材图标的半透明信息卡，根据服务器可见消息显示状态，不伪造没有收到的数据。
- Simes 授权范围不包括市场、估值、余额和自动消息功能；Mana HUD 自 v1.1.4 起纳入授权迁移范围。

### 5.3 mod 3 饰品配装

- 内置饰品工具可从背包或容器扫描、复核、编辑、评分和计算配装。
- 外置桥接 ID：`simmc_travel_hunter_accessory_tool:screen_opener_v1`，协议为 `Consumer<Screen>`。
- 外置维护版存在时优先接管；独立入口和 Tool Set 入口都必须保留。
- mod 3 `6.1.0-fabric` 的独立桥接实现仍需重新确认真实构建、提交和客户端联调状态，不得仅凭线程描述宣称已发布。

### 5.4 mod 4 卷轴计算

- 内置卷轴计算保留原 solver、材料排除、帮助、关于、取消、设置和独立入口行为。

## 6. SIMMC 网页地图与 Xaero

- 地图板块位于发酵与厨具下方，默认组合键为 `\` + `5`。
- 已取得 SIMMC Map 授权并有仓库：`https://github.com/MurphyPotato/SIMMC-Xaero-Map`；本地源文件位于 `I:\mc smc服\simmc moster hunter 2.0\simmc-tool-set_project\子版块源码or源文件or接口\SIMMC-Xaero-Map-main`。
- 已验证运行组合：Xaero World Map `1.39.13` + Xaero Minimap `25.2.16`，Minecraft 1.21.8 Fabric。
- 两个 Xaero 都存在且版本不匹配时：显示“版本不完全兼容，可能启动失败，且可能导致游戏崩溃”的警告，并继续尝试运行地图子模块；失败时只停用地图，不得影响其它模块。
- 缺少任一 Xaero 时显示缺失警告，地图实现不启动；其它子模块继续运行。
- 独立 SIMMC Map 已安装时由独立版接管，整合包不得重复加载内部地图实现。
- SIMMC 覆盖层同时面向 Xaero 世界地图和小地图；缩放、拖动、点击和鼠标归属仍由 Xaero 处理。
- 地图连接、刷新、公开标记、切服/离服清理和运行失败状态必须在地图页和诊断中可见。
- Xaero 与 Mod Menu 外部 JAR 不打包进 Tool Set；`jsoup 1.18.3` 作为构建所需嵌入依赖保留。
- 安装 Mod Menu 时，其 Tool Set 配置入口必须直接打开总控首页并保留同一个父 Screen；没有 Mod Menu 时构建必须剔除入口类和 `fabric.mod.json` 中的对应 entrypoint。

## 7. 配置、诊断与隐私

- 新配置写入 `config/simmc-tool-set/`；旧配置只在新文件不存在且对应外置模块未安装时一次性只读导入，不修改、删除或双向同步旧文件。
- 诊断记录默认只保存在内存，玩家点击导出后写入 `config/simmc-tool-set/diagnostics/`；页面显示最近文件路径并支持复制。
- 不自动上传诊断、截图、凭据、玩家数据或设备标识；不加入遥测和不受控网络通信。
- 地图只访问已授权的数据源；所有后台线程、HTTP 客户端、求解器和状态缓存必须在切服、离服和客户端停止时关闭或清空。

## 8. Git、构建与发布

- 每次功能迭代建立新版本号、独立分支和独立标签；不覆盖旧代码、旧 JAR、旧标签、旧 Release 或旧资产。
- 可分发 JAR 放在项目根的 `release/` 外部目录，不放入 Git 工作树；旁边必须有同名 `.jar.sha256`。
- 发布前至少完成：完整构建、兼容性 smoke、JAR 静态审计、客户端专用审计、版本/依赖审计和工作树检查。
- PowerShell 中使用项目 JDK 21 和 Gradle wrapper；Loader 参数必须使用脚本的明确参数形式，不能让 `-Ploader_version` 被解析成 `0`。
- 构建或测试失败时先记录完整错误和环境，区分依赖下载、Gradle worker、编译、运行时和断言问题，不得把部分成功写成整体成功。
- 当前仓库若没有计划中提到的辅助脚本，应先用 `rg --files` 确认路径；
  JDK 21 与匹配的 Gradle 9.5.0 必须从已缓存/受控路径运行。Gradle、Loom、
  native-platform 或 Git 权限失败先归类为环境问题，不修改源码“修复”它们。

## 10. 问题与解决方案记录

- 初始启动问题：Mixin 类边界过宽会让入口类被误判；通过收窄 Mixin 包路径修复，并保留客户端专用审计。
- Gradle 发行包未缓存时，沙箱网络会拒绝官方下载；使用官方 Gradle 9.5.0 发行包并记录下载环境，不能把网络失败当成代码失败。
- JDK 21 可以使用；本项目已用项目 JDK 21 完成完整构建，不得退回 Java 8 或用不兼容 Gradle 代替 Loom 要求。
- JUnit worker 曾在测试类已生成的情况下报告 `ClassNotFoundException`；改为 `verifyMapCompatibility` JVM smoke task，并让 Gradle `test` 排除该 smoke 类。
- PowerShell `-Ploader_version=0.17.3` 可能解析成 Loader `0`；使用 `run-fabric-gradle.ps1 -LoaderVersion 0.17.3 ...` 的明确参数。
- `run-fabric-gradle.ps1 clean` 会把 `clean` 误绑定为 LoaderVersion；始终先传 LoaderVersion，再传 Gradle 任务。
- `.git/index.lock`、`native-platform.dll` 和离线 Loom 依赖曾阻塞其它子模块验证；遇到时保留未验证状态，不创建伪造提交、JAR 或 Release。
- 版本发布曾出现“直接覆盖”的风险；通过新分支、新标签、外部 release 目录和 SHA-256 文件解决。
- 测试脚本名称必须使用仓库实际命令，例如 `npm run verify:fabric-data`，不要凭直觉拼接任务名。
- 只做源码/编译验证时不能声称 Minecraft 窗口和真实服务器联调已经完成。
- Minecraft 文字颜色参数必须使用带 Alpha 的 ARGB；24 位 RGB 会被当作透明文字，表现为按钮存在但标签空白。
- Litematica 只作为热键页布局参考；其 MaLiLib 依赖不得复制进 Tool Set。
- 隔离 `runClient` 在本轮已到 Fabric/渲染资源加载阶段；Xaero 联网版本检查超时不影响本地启动，但目标服务器和页面点击仍未验证。
- 本轮 Fabric Loom 首次重映射在系统临时目录报 `AccessDeniedException`；将 `TEMP/TMP` 指向项目内 `.gradle-local/loom-tmp` 后 `build -x test` 成功。
- 本轮 Gradle `test` 仍报告 `ClassNotFoundException: worker.org.gradle.process.internal.worker.GradleWorkerMain`；继续使用 `verifyUnitTests` 通过 JUnit Platform Launcher 直接执行测试，并以 `build -x test` 完成构建。后续以该任务的实际计数作为本机单元测试证据。
- 无 Xaero/Mod Menu 构建必须通过资源处理剔除地图 Mixin 和 Mod Menu entrypoint；该矩阵已实际通过。
- Gradle wrapper 必须设置 `GRADLE_USER_HOME` 指向已有项目缓存；否则即使本机已有 Gradle 9.5.0，也可能再次尝试联网下载并因沙箱网络权限失败。
- Loom 项目缓存缺少 `mojang_versions_manifest.json` 时，即使其余 Minecraft 缓存存在也会在配置阶段失败；可从本机已有 Gradle Fabric Loom 缓存复制同一清单后使用 `--offline` 验证，无需重新联网下载。
- 必要时允许在仓库隔离 `run/` 目录运行自建开发客户端；禁止启动、修改或复用用户客户端目录。隔离客户端到达资源加载阶段只能证明相应启动阶段，不等于用户环境、UI、目标服务器功能或完整矩阵验收。
- v1.1.3 与 v1.1.4 构建期间 Xaero Mixin remap 都输出了 GuiMap 方法不存在和 renderOutsidePip 未完全限定警告，但 verifyMapCompatibility 与 build 均成功；该输出需在真实地图 UI 验收时继续观察，不能当作已验证兼容。

## 11. 验收门槛

以下任一项失败都不能标记本版本为完整发布：

- 基线 JDK 21、Loader 0.17.3 下完整构建失败。
- 总控或任一子板块鼠标点击、滚轮、拖拽、聊天输入或原生返回被快捷键破坏。
- 外置模块存在时内置模块重复初始化、重复线程、重复事件或重复配置读写。
- 版本不兼容警告缺失，或地图失败导致其它模块失效。
- 诊断自动上传、泄露凭据或写入未说明目录。
- JAR 错误打包 Xaero/Mod Menu，或缺少必要的 jsoup 嵌入依赖。
- 用户客户端的手工启动、标题/世界/容器路径和父 Screen 行为没有验收证据。

## 13. 测试清单对照与分配流程

每个测试问题/需求必须以当前版本 DOCX 清单重新核对，不继承上一版“已修复”结论。
矩阵至少记录清单编号、原等级、最新指定等级、负责人、文件边界、测试命令、证据和状态。

对照流程固定为：读取并提取 DOCX 正文、表格和嵌入证据；逐条对照当前源代码、测试与运行证据；
将状态分为“已确认未修复”“源码覆盖但运行时未验证”“未复现/暂不修复”和“已解决”；
DOCX 等级与用户最新消息冲突时保留原等级，但以用户最新消息为准；子代理提交后由主线程审阅
差异、API、测试和越界修改；构建后再次逐条复核，未纳入本轮的等级不得因构建成功而清除。

通用分类与资源分配模板：

| 等级 | 范围 | 资源 | 文件/职责边界 | 状态规则 |
| --- | --- | --- | --- | --- |
| P4 | 纯文案/说明 | 1 个 gpt5.6-LUNA-MAX | 总控和静态说明，不改动态快捷键、地图逻辑或奥术运行时 | 静态核对后再标记 |
| P3 | 轻度功能/机制 | 2 个 gpt5.6-LUNA-MAX | 动态快捷键读取与显示；共享文件顺序交接 | 逐条验证 |
| P2 | 体验或中等修改 | 本轮不单独分配 | 若被其他修复顺带覆盖，必须单独复核 | 否则未修复/待验证 |
| P1 | 不可用或较大恢复 | 1 个 gpt5.6-Sol-xhigh | 授权 Simes 奥术 HUD及测试，不改总控、快捷键、地图或版本入口 | 需针对性测试，实机仍待验收 |
| P0 | 崩溃或重大变更 | 主线程 | 共享入口、生命周期、整合和发布门槛 | 当前清单无 P0 |

v1.1.4 从 `b9acb09` 建立独立分支：P4/P3 由一个 LUNA-MAX 子代理负责总控页面，P2/P1 由一个 Sol-high 子代理负责 Simes 奥术范围，主线程负责生命周期、整合、构建、逐条复核和记忆同步。地图按钮对齐已由 P3 页面改动一并完成；发酵/厨具仍按清单保守保留。

## 12. 后续更新协议

每次回答结束前检查四类新增信息：

1. 新的用户明确需求或边界。
2. 新发现的问题及可复现解决方案。
3. 新的测试证据、提交、标签、产物或未验证状态。
4. 已被替代的旧决定。

只有出现持久信息时才更新本文件和私有记忆；没有新事实时不追加空记录。更新时同步修改“当前状态”“已完成/仍需完成”“问题记录”和“决策日志”，并在 Git 中使用独立文档提交。私有记忆保留更详细的错误上下文，但必须带项目作用域，不能作为其它项目的默认约束。
